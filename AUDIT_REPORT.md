# PocketTrack — Multi-Persona Audit Report

Produced from `AUDIT_PROMPT.md` and `Claude_Code_Audit_Master_Guide.pdf`, against the source in `src/` as it stands today.

---

## Verdict

PocketTrack is a well-built shell around a ledger that loses money.

The engineering fundamentals are sound. TypeScript compiles clean, the production build succeeds, there are zero dependency vulnerabilities, and the Dexie write path correctly wraps balance mutations in atomic transactions. The Indian-market thinking is real and not cosmetic: Swiggy, Blinkit, chai, auto, UPI, GPay and lakh are first-class in the data model and the parser.

Underneath that, three defects destroy user money or user data, and each one sits on a path a normal user will take in their first week. A fourth class of problem is that several trust signals on the dashboard are fabricated: the streak badge and the percentile badge are hardcoded strings, and the demo buttons in the balance explainer write real, unremovable transactions into the ledger.

The product is also not legally launchable. There is no privacy policy, no terms of service, no financial disclaimer, no consent surface, no full data export, no account deletion, and no row-level security policy anywhere in the repository, while the app stores complete financial histories and can transmit them to Supabase.

**Recommendation: do not launch. The three Critical defects and the nineteen High defects are a focused body of work, and the code is close enough that fixing them is a matter of days, not a rewrite.**

## Persona 1. Principal QA Engineer and Code Auditor

**104 confirmed defects: 3 Critical, 19 High, 43 Medium, 39 Low.**

### The three that destroy money or data

**1. The "Guide" button in the header deletes everything.** `src/App.tsx:388`

The header offers a friendly control labelled "Guide", titled *Reopen Welcome Explainer & Overview*. It returns the user to the first-run onboarding screen. That screen has exactly two ways out, and both of them call `db.initializeCleanVault()`, which runs `transactions.clear()` and `accounts.clear()` with no confirmation and no data check. There is no "back to my vault" button anywhere on it.

Worse, the "Get Started" path writes `pockettrack_stage = 'auth'` to localStorage before it wipes. Once that is written, closing the tab and reopening the app lands the user on the setup screen permanently, and the only way forward from there also wipes. The escape hatch of reloading the page stops working the moment they touch that button.

Note the inconsistency: the explicit "Reset vault" action in the same menu *is* guarded by a confirmation dialog. The dangerous path is the unguarded one.

**2. Transfers debit one account and credit nobody.** `src/components/transactions/TransferModal.tsx:24`

Both transaction modals capture their account selection like this:

```ts
const [fromAccountId, setFromAccountId] = useState<string>(accounts[0]?.id || '');
const [toAccountId,   setToAccountId]   = useState<string>(accounts[1]?.id || '');
```

These modals are mounted unconditionally by `App.tsx`, so the initialisers run on the app's very first render. At that moment `useLiveQuery` has not resolved and `accounts` is an empty array, so both values are the empty string. The initialiser never runs again, and there is no effect anywhere that re-syncs them.

The trap is that the form still *looks* correct. A `<select>` whose value matches no option displays its first option, so the user sees a real account name while the state holds `''`. The only guard compares the two ids to each other, which passes as soon as the user touches one dropdown. The transfer then reaches `addTransaction`, which debits the source and skips the credit because `if (data.toAccountId)` is false.

Money leaves one account and arrives nowhere. Net worth drops by the transfer amount.

The same root cause blocks the typed-entry path entirely: a user with a single account, which is what every new vault has, gets "Please select an account" on their first save, forever.

**3. Voice transfers vaporise the amount.** `src/components/transactions/VoiceLogModal.tsx:108`

The parser classifies a sentence as a transfer whenever it contains "transfer" or "moved", but it only fills in a destination when *two different* accounts match the sentence. A new vault has one account, so the destination is almost always empty. The voice modal validates the amount and the source account, and never checks that a transfer has a destination.

Executing the real parser against a real single-account vault:

```
'transferred 5000 to savings'           -> type=transfer  from=acc-primary  TO=undefined
'moved 15000 from checking to savings'  -> type=transfer  from=acc-primary  TO=undefined
'transfer 2000 to my fd'                -> type=transfer  from=acc-primary  TO=undefined
```

Feeding the first of those into the real balance logic: source 58,400 becomes 53,400, destination unchanged, 5,000 rupees gone.

There is a second bug hiding in the same place. With the four-account demo set, "transferred 5000 to savings" picks **savings as the source**, because the parser assigns accounts in database order rather than by their position around the words "from" and "to". The one account the user named as the destination becomes the account that gets debited.

### Evidence I executed rather than read

These were produced by transpiling the real modules and running them, not by reading the code.

**The parser loses digits.** A comma anywhere in the amount truncates it, and the app still reports 95% confidence:

| Spoken or typed | Amount stored | Confidence | Category |
|---|---|---|---|
| `Spent 1,200 on groceries` | **1** | 0.95 | Groceries |
| `Paid 1,250.50 for medicines` | **1** | 0.95 | Food, not Health |
| `bought a coffee` | **1** | 0.95 | Food |
| `an auto to college` | **1** | 0.95 | Transport |
| `Got cashback of 50` | 50 | 0.95 | **Salary**, not Cashback |
| `Ordered Swiggy for 450` | 450 | 0.95 | Food, correct |

Three separate faults are visible here. `a` and `an` are mapped to the number one, so any sentence without digits produces a one-rupee expense at high confidence. The amount regex stops at a comma. And the health keyword is written as `\bmedicine\b`, which fails against the plural "medicines", so the expense falls through to the Food default.

**The same spend lands in two different months.** For a user in India logging at 00:30 on the first of a month, the timestamp stored is `2026-09-30T19:00:00.000Z`. The dashboard matches months by string prefix against local time and excludes it from October. The budgets page uses a UTC-shifted window and includes it in October. Two screens, two answers, same transaction.

**The budgets page goes stale at midnight.** Its month window is computed once when the component mounts, with an empty dependency array. A window captured at 23:50 on the 30th silently stops counting anything logged the next morning until the page is reloaded.

**The date picker is wrong for the Americas.** Picking 1 October stores UTC midnight, which renders as **30 September** in New York and Los Angeles. Every manually dated transaction is off by one day for negative-offset users.

**Balances drift.** Ten expenses of 20.10 against a 2,000 balance leave `1799.000000000001`. Balances are floats mutated in place with no rounding at the write boundary.

**The CSV export truncates.** The file is built as a `data:` URI passed through `encodeURI`, which does not escape `#`. A note reading "Order #1234 refund" ends the file at that character. Values beginning with `=`, `+`, `-` or `@` are also passed through unescaped, which is spreadsheet formula injection.

**The savings projection overstates.** At 15,000 per month, 12%, ten years, the app's annuity-due formula returns 34,85,086 where the ordinary-annuity convention that every Indian SIP calculator uses returns 34,50,580, a gap of about 35,000. Neither figure is adjusted for inflation; in today's money the real result is closer to 19,46,000, which the interface never shows.

### Fabricated trust signals

Three things on the dashboard are not real, and users will discover all of them.

- The **"7-Day Logging Streak"** badge at `FinancialHealthScore.tsx:95` is a hardcoded string. No streak is computed anywhere in the codebase. A brand-new vault with zero transactions displays a seven-day streak.
- The **"Top 15%"** percentile badge on the same card is likewise a literal, with no cohort data behind it.
- The **"Tap to test"** buttons in the balance explainer write real transactions into the real ledger. Since the app has no edit-transaction feature at all, a curious first-time user permanently pollutes their books and can only delete.

### High-severity findings I re-checked by hand

Seven of the nineteen were traced to the source individually rather than accepted from the pipeline.

**Cloud sync can never run, for a subtler reason than it first appears.** `SyncContext.tsx:34`. The only caller of `triggerSync` is the browser's `online` event handler. That handler closes over the version of `triggerSync` built while `isOnline` was still `false`, and the first thing `triggerSync` does is `if (!isOnline || isSyncing) return`. So the reconnect path returns immediately. The effect then re-registers a fresh handler, but no second `online` event ever arrives. There is no trigger on mount, on login, after a write, or on a timer. Nothing is ever uploaded.

**Every quick-tap button logs to the wrong account.** `QuickTapBar.tsx:21`. The six preset chips name accounts `acc-cash`, `acc-checking` and `acc-credit`. Those ids only exist in `defaultData.ts`, which the app never inserts; real onboarding creates a single account called `acc-primary`. The lookup fails and falls back to `accounts[0]`, so the chip advertising a credit card charges cash. The confetti and the sound also fire before the write is awaited.

**The "Copy UPI ID" button fabricates a payment address.** `BankCardCarousel.tsx:20`. It builds `${accountName}@okaxis` by stripping non-letters from whatever the user typed as an account name, and copies that to the clipboard. An account called "HDFC Salary Account" yields `hdfcsalaryaccount@okaxis`. That string is not the user's handle. Pasted into a payment app it may well resolve to a stranger, and the interface presents it as the user's own.

**Setting a budget to zero deletes the budget forever.** `BudgetsView.tsx:41`. The editor accepts any value `>= 0`, so zero is stored. The budgets hook then filters on `cat.budgetLimit && cat.budgetLimit > 0`, which drops the category. The page renders only that filtered list, so the category is gone from the one screen that can edit it. Worth noting: the component's props declare `allCategories`, and `App.tsx` dutifully passes it, but the component never destructures it. The prop that would have provided the way back is dead code.

**The reset dialog understates what it does.** `Header.tsx:59`. The text asks to "Reset vault to clean slate with 0 transactions?". The function it guards also deletes every account the user created and inserts a fabricated "UPI Wallet & Cash" holding 2,000 rupees they never had. It leaves the savings goals and subscriptions in localStorage untouched, so a "reset" vault still shows the old goals.

**Deleting a transaction takes one tap, with no confirmation and no undo.** `RecentTransactions.tsx:192`. The handler is `onClick={() => onDelete(tx.id)}`. The returned promise is neither awaited nor caught, so a failed delete is silent. Since there is no edit feature anywhere in the app, delete-and-retype is the only correction path, which makes the missing guard worse.

**The CSV export is the only export, and it is lossy.** `TransactionHistoryView.tsx:64`. Beyond the `#` truncation and formula injection above, it omits the destination account on transfers entirely, and it writes full amounts in plaintext even while privacy mode is masking the screen.

### Security claims the code does not support

I checked these directly because they carry legal exposure rather than merely being bugs.

| Claim shown to users | Where | Reality |
|---|---|---|
| "Secure end-to-end cloud backup" | `AuthModal.tsx:49` | Sync upserts thirteen plaintext columns, including free-text notes, to Supabase. There is no encryption anywhere in the codebase. |
| "Encrypted cloud backup" | `Sidebar.tsx:178` | Displayed to every signed-in user. Same reality: nothing is encrypted client-side. |
| "Zero data sharing... offline secure" | `WelcomeExplainer.tsx:134` | Shown on a page that loads fonts from a Google CDN, in an app whose voice feature streams audio to Google's speech servers. |

The third of these is arguable marketing. The first two are statements of a specific security property that the product does not have, in a financial application. They should be removed or made true before anyone sees them.

## Where the data lives

Anyone writing the privacy policy needs this inventory. It was produced by grepping the source, not from documentation.

**IndexedDB, database `PocketTrackDB` version 1:** `accounts`, `transactions`, `categories`, `budgets`, `subscriptions`, `sync_queue`.

Two of those tables are dead. `budgets` and `subscriptions` are declared in the schema and never written to. Budget limits live on the category record instead, and subscriptions live in localStorage.

**localStorage, thirteen keys:** `pockettrack_checklist_dismissed`, `pockettrack_currency`, `pockettrack_goals`, `pockettrack_guest_mode`, `pockettrack_lang`, `pockettrack_last_sync`, `pockettrack_math_guide_collapsed`, `pockettrack_mobile_frame`, `pockettrack_privacy_mode`, `pockettrack_stage`, `pockettrack_subscriptions`, `pockettrack_tour_completed`, `pockettrack_username`.

Two of these hold real financial records rather than preferences. `pockettrack_goals` holds every savings goal and its balance, and `pockettrack_subscriptions` holds every recurring bill. Neither is covered by the CSV export, neither syncs, and both vanish if the user clears site data.

**Supabase, one table:** `transactions`, with columns `id`, `user_id`, `account_id`, `to_account_id`, `category_id`, `amount`, `type`, `date`, `notes`, `tags`, `receipt_url`, `created_at`, `updated_at`.

Accounts, categories, goals and subscriptions never leave the device. Combined with the sync defect, neither do the transactions in practice.

## Method and provenance

This audit ran in two passes over the same source.

The first pass used six subsystem auditors, each assigned a cluster of files, followed by a deduplication step, a batched adversarial verifier per subsystem whose instructions were to refute each claim rather than confirm it, a completeness critic, and a second round of finders aimed at the gaps the critic identified. It produced 118 raw reports, which deduplicated to 95 distinct defects, of which 88 survived verification. The gap round added 16 more. Two claims were refuted outright and five were left unresolved.

The second pass re-ran all six persona reviews on Opus 5, independently, with the executed evidence above supplied as established fact. The persona judgements, scores and recommendations in this report, and the feature cards built from them, come from that second pass.

The three Critical defects were not taken on trust from either pass. Each was traced through the source by hand and then reproduced by executing the real modules, and the transcripts of those executions appear in the QA section above.

What this audit did **not** do: run the application in a browser, test on a physical phone, measure real rendering performance, or verify anything about a Supabase project, since no credentials or schema exist in the repository. The five unresolved findings are unresolved precisely because settling them needs a real device.
